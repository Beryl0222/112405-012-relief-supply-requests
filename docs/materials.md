# 资料口径

瓶装水每箱24瓶，每箱占2体积格；滤芯每箱6个，占1格；泵滤套装含泵1台、滤芯2个，占4格。盘点是时刻存量，不是新增订货。数量未确认时不补造。

`data/case.json` 使用 UTF-8，`case_id` 是一次业务资料包编号；`records` 保存原始文本，`id` 稳定，`kind` 说明资料种类，`text` 保留原文。来源的陈述可未核实、互相冲突或被后续文字更正，编号顺序不是业务效力优先级。

`objects` 是对象、关系或场地的业务登记；其中 `source` 和 `sources` 引用原文编号。`existing` 是已经存在的办理记录，`state` 记录当时所处阶段；历史文字可能与后补事实不符，不表示当前仍可采用。接收后补资料时，应保留其原文和独立编号，使用者的解释确认也要能对应具体原句版本。不能因来源有引用便把转述当独立观察。

相同格式可容纳新的对象和原文，不用记录编号表示固定结论。资料中出现的姓名、地点、金额、规则和专业术语均为合成演练内容，不对应真实业务资质。

## 办理链路（relief 包）

`relief/` 是只追加事件驱动的办理链路，事实来源是事件日志，不是翻译后的优先级表：

- `parser.py`：中英双语规则解析。数量必须带单位，时钟（`十一时`、`09:30`、`九时半`）与型号编号（`F2`）不会被误当数量；区分“再要”（追加）与“总共要”（总量）；语义不明产出具体澄清而不猜测。
- `model.py` / `catalog.py`：物资目录、包装占格与套装构成。F1 与 F2 是不兼容型号；泵滤套装按部件缺口拆单件，部件不齐不整套承诺。
- `events.py` / `commands.py` / `state.py` / `engine.py`：命令先过不变量校验再追加事件，状态由事件回放得到。库存不重复占用、车位不挂两张有效单、容量/窗口/可达性、已装车不自动回库、改送按实际卸货重判都在引擎强制。
- `allocation.py`：按核验后的缺口、可用库存与车辆约束生成可兑现装车计划，逐条解释拒绝原因；条件替代未满足前保留后备份额。
- `readmodel.py`：缺口看板（缺口/在途/备货/未解决/耗尽时刻）、库存、承诺、澄清与冲突的只读投影。
- `store.py` / `service.py` / `cli.py`：JSONL 事件持久化、幂等接入（同原文重复办理不产生重复效果）与命令行查询。

### 占格与数量口径

水按箱（2 箱/24 瓶口径见上）；滤芯整箱 6 个密封占 1 格，散件每个 1 格（与 RS-G “实装四个 F2、两箱水，剩一格”一致：4 格 + 2×2 格 = 8 格，T1 容量 9 格余 1 格）；泵每台 2 格；泵滤套装整套 4 格。盘点是时刻存量，核验后才进入有效口径，核验有效时段随盘点登记。
